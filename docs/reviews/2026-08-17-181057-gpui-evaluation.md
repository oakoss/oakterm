# GPUI Evaluation

## Scope

[ADR-0018](../adrs/0018-gpu-rendering-wgpu.md) chose wgpu over raw native APIs, Skia, and OpenGL — but never considered GPUI, Zed's GPU-accelerated UI framework. That omission is conspicuous: Zed ships a fast terminal on GPUI, and the [agent-tooling landscape audit](2026-08-16-215731-agent-tooling-landscape-audit.md) noted Zeron's ground-up Electron→GPUI rewrite. This review evaluates GPUI's current state (all claims verified against the Zed source tree and crates.io on 2026-08-17) and whether it belongs in ADR-0018's option set.

## GPUI as of 2026-08-17

**Standalone status.** GPUI became an officially published crate in October 2025: `gpui` 0.2.2 (2025-10-22, Apache-2.0, ~195k downloads for that version, ~208k crate-wide). But publishing has since stalled — no crates.io release in ten months — while the in-tree framework was restructured into a crate family (`gpui_platform`, `gpui_macos`, `gpui_windows`, `gpui_linux`, `gpui_web`, `gpui_wgpu`) of which none are published. Consuming current GPUI means a git dependency on the Zed monorepo. Pre-1.0; breaking changes between versions are routine.

**Rendering backends** (from the crate family's manifests and sources):

| Platform      | Backend                                | Shaders | Text                                  |
| ------------- | -------------------------------------- | ------- | ------------------------------------- |
| macOS         | direct Metal                           | MSL     | Core Text via zed-font-kit (git fork) |
| Windows       | direct DirectX (`directx_renderer.rs`) | HLSL    | DirectWrite                           |
| Linux/FreeBSD | **wgpu** (`gpui_wgpu`)                 | WGSL    | font-kit                              |
| Web (wasm)    | **wgpu** (`gpui_wgpu`)                 | WGSL    | —                                     |

Linux moved off blade onto wgpu in early 2026 (third-party reporting cites Zed v0.225.9, 2026-02-25, after graphics-backend instability; the `gpui_linux` → `gpui_wgpu` dependency confirms the current state). Platform maturity ordering is macOS > Linux > Windows (Windows support landed October 2025).

**What GPUI is.** A full application framework, not a rendering abstraction: it owns the event loop and windowing (no winit), layout (taffy), its own text system, accessibility (AccessKit integrated), and a hybrid immediate/retained element tree. The renderer is not separable from the framework.

**Terminal prior art on GPUI.**

- **Zed's terminal**: `alacritty_terminal` for PTY/VT, custom `TerminalElement` for cell rendering. Production-proven, fast.
- **tty7** (l0ng-ai/tty7, Apache-2.0, ~735 stars): a "terminal workbench" on GPUI + `alacritty_terminal` with a daemon/client split, persistent sessions, native SSH, and coding-agent integration — near-direct overlap with OakTerm's product territory, claiming ~2x throughput vs Alacritty/kitty.
- **Zeron**: Electron→Rust/GPUI rewrite (per the 2026-08-16 landscape audit).

GPUI is demonstrably viable for high-performance terminal rendering; a performance argument against it would be wrong.

## Findings

### Validated Decisions

**ADR-0018 Option A (wgpu) is strengthened, not challenged, by GPUI's trajectory.** GPUI itself converged on wgpu for every platform where it doesn't hand-maintain a native backend — Linux moved to wgpu after blade instability, and the web target is wgpu-only. Adopting GPUI would not remove wgpu from the stack; it would move wgpu from behind OakTerm's own trait seam to behind Zed's framework, while reintroducing on macOS/Windows exactly the three-backend/three-shader-language maintenance surface ADR-0018's Option B was rejected for (carried by Zed rather than OakTerm, but its churn flows to consumers pre-1.0).

**The layer mismatch is the decisive argument.** ADR-0018 decided a GPU abstraction under a renderer OakTerm owns. GPUI is one layer up: adopting it replaces winit, the event/render loop, the glyph atlas, the a11y bridge, and the layout of every surface — it would supersede ADR-0018 rather than slot into its option list. And GPUI's core value (widget trees, taffy layout, element composition) targets precisely the surface OakTerm deliberately doesn't have: chrome (status bar, tab bar, palette) renders as terminal cells through the same atlas and shader as the grid.

**Nothing measured motivates a switch.** The [2026-07-02 parity benchmark](2026-07-02-114749-wgpu-parity-benchmark.md) put ingest at 1.2x Ghostty with nothing implicating wgpu; the one large gap was daemon-side (TREK-191, fixed). If the frame/latency gate (TREK-192, open) ever did implicate wgpu on macOS, GPUI's direct-Metal backend would remove that overhead — but so would ADR-0018's reserved escape hatch: carve the GPU trait seam the abstraction principle mandates (designed but not yet built — `GpuState` in `crates/oakterm/src/gpu.rs` is concretely wgpu today) and swap the macOS backend behind it. That is renderer-scoped work; adopting a full framework to reach Metal is a whole-client rewrite.

**Consumption risk is real today.** Pre-1.0, single-vendor (roadmap = Zed's needs), publishing stalled mid-restructure, git-dependency required for current code, and a forked font-kit in the dependency tree.

### Challenged Decisions

**None on substance — one on completeness.** ADR-0018's option set omits the most obvious "why not?" candidate. The record should show GPUI was considered and why it was rejected, so the question doesn't recur.

### What would change the calculus

1. **Phase 2 plugin UI surfaces.** If plugin dashboards outgrow cell-rendered chrome and need real widget trees, the framework question reopens — but as a Phase 2 ADR about plugin surfaces, not a renderer swap. Re-check GPUI's publishing cadence and API stability then.
2. **TREK-192 gate failure** is remedied by the raw-Metal escape hatch — carving the mandated GPU trait seam and swapping the backend, renderer-scoped work versus the whole-client rewrite GPUI requires for the same direct-Metal access.
3. **tty7** deserves tracking as competitive prior art independent of the framework question: daemon/client persistence + SSH + agent integration is OakTerm's roadmap shipped early on borrowed parts (GPUI + `alacritty_terminal`).

## Action Items

- **ADR amendment (applied 2026-08-17):** [ADR-0018](../adrs/0018-gpu-rendering-wgpu.md) now records "Option E: GPUI" as evaluated and rejected — layer mismatch, wgpu-underneath-anyway, pre-1.0 consumption risk — with a pointer here.
- **Landscape tracking:** add tty7 to the competitive-landscape material alongside Warp/Zeron.
- **No change** to TREK-192 or the ADR-0018 gate.
